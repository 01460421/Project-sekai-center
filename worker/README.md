# 逐局活動P 追蹤器（Cloudflare Worker + Durable Object）

前 50 名玩家「每一局加了多少活動P」。每 15 秒掃一次即時排名，只記有變動的那筆。

## 為什麼是這個架構

| 選項 | 結論 |
|---|---|
| Cron Trigger | 表達式最小粒度是**分鐘**，做不到 15 秒 |
| **Durable Object alarm** | `setAlarm()` 吃絕對毫秒數，`Date.now()+15000` 完全合法——Cloudflare 上官方唯一支援的 sub-minute 排程 |
| GitHub Actions 常駐 | **不要用**。違反附加產品條款（禁止「把 Actions 當 serverless 應用的一部分」、禁止「與 repo 專案無關的活動」），且排程交接每天最多 2 小時空窗 |

15 秒是實測推導的：一場協力最短約 150 秒（曲長＋結算＋房間），15 秒間隔絕不會把兩局
併成一筆，時間戳誤差 ±15 秒。再密只是多打人家的 API，換不到更多資訊。

## 部署（需要你自己執行，會用到你的帳號與付款方式）

```bash
cd worker
npx wrangler login          # 開瀏覽器授權
npx wrangler deploy
curl https://pjsk-games.<你的子網域>.workers.dev/ensure   # 啟動 alarm 鏈
```

**需要 Workers Paid（US$5/月）。** 免費版每次 invocation 只有 10 ms CPU，而我們每輪要
解析 120KB JSON 再做 50 人差分，沒有安全邊際（官方 FAQ 明說 DO 與 Worker 的 CPU 上限相同，
文件裡的 30 秒是付費版預設）。付費版 30 秒，綽綽有餘。

額度用量（付費版上限更高，這是對照免費版的比例）：

| 項目 | 每日用量 | 免費上限 | 佔比 |
|---|---|---|---|
| alarm invocation | 5,760 | 100,000 | 5.8% |
| 運算時長 | 約 432 GB-s | 13,000 | 3.3% |
| rows written | 約 23,000 | 100,000 | 23% |

## 端點

| 路徑 | 用途 |
|---|---|
| `GET /status` | 目前活動、累計局數、失敗次數、下次 alarm 時間 |
| `GET /games?ev=176&since=0&uidx=3` | 前端讀取。`since` 增量拉、`uidx` 只拉單一玩家 |
| `GET /ensure` | 沒排程就補排（看門狗每分鐘打這支，也可手動啟動） |
| `GET /stop` | 手動停止（維護用） |

`/games` 回傳精簡陣列 `[玩家索引, 相對秒數, 增量P, 當下名次]`，每局約 17 bytes；
整期前 50 名推估約 1.6 MB。

## 幾個刻意的設計

* **只做前 50 名** — API 只有前 100 名有本期活動分數，非前百查不到，不是偷懶。
* **19 位 uid 先轉字串** — 超過 IEEE754 安全整數，直接 `JSON.parse` 會讀成失精的浮點數。
* **時間存「相對活動開始的秒數」** — 比絕對時間短很多，是每局能壓到 17 bytes 的原因之一。
* **新玩家進榜的第一筆不算增量** — 沒有基準值，算了會是假的一局。
* **中斷超過 3 個週期記一段 gap** — 那段的增量是多局合併，前端要誠實標示，不能假裝完整。
* **alarm 先排下一棒再做事** — 本輪就算拋錯，鏈也不會斷。
* **非活動期自動停掉 alarm** — 不空轉、不打人家 API；每分鐘的看門狗會在活動開始後喚醒。
* **上一輪分數存在 SQL 不是記憶體** — DO 會被驅逐，記憶體留不住，醒來就少算一局。

## 看門狗為什麼必要

alarm 有 at-least-once 保證，但 handler 拋錯只會用指數退避重試 **6 次**；遇上來源站較長的
故障，重試耗盡後這條鏈就永久斷掉、靜悄悄不再跑。所以另外掛每分鐘的 Cron Trigger，
只做「沒排程就補排」這一件事。
