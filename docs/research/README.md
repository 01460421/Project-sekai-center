# 升學備考 App — 研究產出（未完成）

把 Project SEKAI 資源中心當模板，重做成一個涵蓋**國中會考、高中學測與其他大型考試**的
跨平台（iOS / Android / 桌面 / 網頁）備考 App。這個目錄是規劃階段的研究資料。

## ⚠️ 這份研究只做完一半

原本規劃 36 個研究代理分三軸並行，**在第 19 份完成時中止**。
中止的代價寫在最下面「缺什麼」那一節 —— 特別是**三個合成階段與三個批判階段都沒有跑到**，
也就是「一個人＋AI 到底做不做得完」這個問題**還沒有答案**。

要續跑的話，`工作流腳本/` 裡有三支完整腳本，可以直接重跑或只挑沒跑完的部分跑。

## 六個已經確定的結論

**1. 著作權：情況比預期好很多，但界線要記牢。**
著作權法 §9 明定「依法令舉行之各類考試試題及其備用試題」不受著作權保護，
**大考中心學測題、心測中心會考題、統測題可自由商業利用**。
但官方試題分析、詳解、六級分樣卷受完整保護；學校段考卷不算「依法令舉行之考試」，
出題老師享有著作權；均一／PaGamO／學習吧的平台自製題不在 §9 之列。
另外，教育部《重編國語辭典》《成語典》是 CC BY-ND 3.0 TW（可商用，不得改寫釋義）、
PhET 互動模擬是 CC BY 4.0（可直接嵌入商業 App）。

**2. `support.js` 的 dc-runtime 必須丟棄。**
`compileTemplate()` 依賴真實 DOM 遍歷、`parseDcText()` 用 `DOMParser`、
`evalDcLogic()` 用 `new Function()`。React Native 的 Hermes 不支援 eval——
這是執行期崩潰，不是相容性問題。要搶救的是設計 token、`app.html` 裡的領域邏輯、
以及整個 Worker 後端。

**3. D1 是架構級死路。**
以註冊 30 萬、DAU 6 萬、每人每日 200 筆答題事件估算，答題事件是 2.16 GB／日，
**4.6 天撞上 D1 的 10 GB 上限**。而 `rows read` 計的是掃描列數不是回傳列數。
Workers 全部留下，D1 降級成控制面小庫。

**4. 離線同步要三層分離。**
GB 級題庫走 CDN 分包、完全不進同步引擎；答題紀錄走 append-only op-log
（兩台裝置各答一題在語意上不衝突，聯集去重即可）；複習排程與統計是衍生狀態，
**永遠不同步、只重算**——同步 `due_at` 是災難的來源；筆記內文用 Yjs，
但當成一種 op 走同一條管線。

**5. 現有設計語言的氣質可留，數值必須全改。**
`css/core.css` 裡 `rem` 出現 0 次，字級全寫死 px（11px 37 次、13px 27 次、
12px 26 次、10px 16 次）——寫死 px 等於 iOS Dynamic Type 不可能實作。
`--text-light` 對比只有 3.06:1，六種色調的強調色沒有一個達到 4.5:1。

**6.「詳細講解」是一份可被 lint 檢查的規格，不是形容詞。**
一個單元 = 一份 `.unit.md`，含 14 個編號固定的區塊；例題七欄位缺一不得上架
（其中「想法起點」必須寫成可遷移規則，禁止寫「憑經驗」）；
三種閱讀深度是同一份原始檔的三個投影，不是三份文件；
S13 的考點統計一律由題庫查詢填值，作者不得手寫任何統計數字。

## 內容量的實數

| 科目 | 條目 | 題庫 | 工時 |
|---|---|---|---|
| 國文 | 3,500–5,000 | 1,000–3,000 題 | 核心版 3–4 人月、完整版 8–12 人月 |
| 英文 | 11,000–14,000（詞彙佔七成） | 1,500–1,700 題 | 三期，第一期 2–3 週 |
| 數學 A/B | 320–400 公式卡＋240–300 題型 | 1,300–1,800 題 | 撰稿 320–420 小時＋標註 90–120 小時 |
| 自然 | 900–1,300 卡＋57 unit | 1,200–1,800 題 | 完整 500–800 人時、MVP 180–250 人時 |
| 考招制度 | 4–6 萬字＋150–200 個逐年更新欄位 | — | 初版 3–4 人週＋每年 1–2 人週維護 |

上面只是**學測五科**。會考六科、社會科、以及「每個單元都要 14 區塊完整規格」的乘數
都還沒算進去。這就是這個專案真正的規模。

## 缺什麼

沒跑完的 17 個代理：

- **內容與設計軸**：社會科範圍、人性化設計理念（學習科學與考生心理／資訊架構／內容工程）
- **平台與系統軸**：完整備考流程設計、自適應出題與能力評估（IRT/CAT/知識追蹤/FSRS）、
  AI 家教與自動批改、題庫與內容工程、動機設計與人性化守則
- **深度與方法軸**：資料庫與資料工程（完整 DDL）、內容生產與品質關卡、
  讀書方法研究與制度化、競品深度拆解、功能窮舉與互聯、學習分析與持續優化
- **三個合成階段與三個批判階段**——包含「產能估算是否誠實」「一個人做得完嗎」
  「最務實的縮減版本是什麼」這些關鍵問題

## 還沒拍板的事

1. 先做哪個考試（會考的使用者基數大、內容淺；學測的付費意願高、內容深）
2. 四個平台的優先序，以及第一版要不要就上四個
3. 內容自製、授權、還是先只做骨架
4. 要不要收費（一旦收費，iOS 必須走 IAP 抽 15–30%，且不能導向外部付款頁）
5. 沿用這個 repo 與網域，還是另開
6. 要不要保留登入與 AI 助手（Worker 後端的沿用率取決於這個）
